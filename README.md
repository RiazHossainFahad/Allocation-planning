# Large-order allocation: crash-safe "journaled" allocator beside the legacy one, large orders on their own cron, phased rollout

## Naming

| Name | Meaning |
|---|---|
| **legacy** allocator | today's `AllocateStandardOrderHelper`. Edited only for the four targeted fixes in Step 1 (each behind a config toggle). |
| **journaled** allocator | new engine: every reservation is written to a journal, so a crash can always be undone. Free to restructure internally; its final result must equal the (fixed) legacy result. |

## Context

A ~4700-line order was killed by the Horizon worker timeout (`config/horizon.php:266`: `timeout 180`, `retry_after 185`, `tries 1`, `maxProcesses 1`) mid-allocation. Root cause (`app/Helpers/Allocation/AllocateStandardOrderHelper.php`):

- Reservation is committed **per line** (`allocateLocationForBinsOnlyLocationPriority` :589 → `updateAllocatedQtyInInventory` :1109, own tx), but picking tasks (:1254), master `inventories` (`updateCentralInventory` :1290) and order status (:1321) are written **once at the very end** (:129-134). Any kill/exception in between leaves `allocated_qty` reserved with no task behind it (orphans). The `catch (\Throwable)` at :135/:200 only logs, so non-timeout failures are hidden too.
- A timeout kill skips the listener `catch`, so `orders.is_allocating` stays 1 and both `process:standard-order` (filters `is_allocating = false`) and the manual endpoint (`OrderController:2547`) skip the order.
- Cross-allocator race: candidate balances are read with no lock (:1741), then `updateAllocatedQtyInInventory` clamps `available_qty` at 0 (:1125) instead of detecting a lost race.
- `lockForUpdate()` at :1277 runs outside any transaction (no-op).
- Cost: ~2-4 balance queries per line (correlated `whereHas` + ORDER BY scalar subquery) + 1 tx per line.

`InventoryBalance`, `Inventory`, `StandardOrderPickingTask`, `AssignmentablePicking`, `Order` are all on the `portal` connection, so one DB transaction can span every write of a finalize.

Assumed environment (standard, no proprietary setup): MySQL 8.0 defaults (`innodb_lock_wait_timeout` 50s, `max_allowed_packet` default), Redis for cache/queue (`.env.example`: `CACHE_DRIVER=redis`), no connection-pooling proxy. Nothing is read from `my.ini`/`my.cnf`. The only runtime probe is a single `SELECT @@max_allowed_packet` per run (cheap, safe) to cap insert batch sizes; everything else is a config value.

## Step 1 — The identity contract and the legacy fixes

Definition (yours): the internal shape may change; the final result must equal the legacy result for every scenario. Because legacy is now fixed too, **"legacy" below means legacy with the Step 1 fixes**, and the journaled allocator is held to exactly that.

### Fixes applied to the legacy allocator (all four read toggles in `config/allocation.php` → `legacy_fixes`; A, C and D default **on**, **B defaults OFF** by your decision; any toggle can be flipped without a deploy)
- **A. `pass2_remaining_qty`.** In the bins-only and default priority branches (:259-264, :276-281) the second pass restarts from the *original* `pending_qty` because `$data['pending_qty']` is never reduced (:574). Example: need 10, exact-barcode balance 6, other-barcode balance 20 → today allocates 6 + 10 = 16 (over-allocation). Fix: before the second call, set `$data['pending_qty'] = $left_allocated_qty` from pass 1, so pass 2 only asks for the remainder (and the returned `left` is the true shortfall that feeds the next rule's `pending_qty`).
- **B. `full_carton_flag`.** `applyIsAllocatedFullCartonFlags` (:1020) tests an undefined `$carton_numbers` and always returns early, so `is_allocated_full_carton` is always `false` and everything below it is dead. Fix: `$carton_numbers = array_keys($new_allocations_by_carton)` before the empty check; compare `round($total,2)` with `round($carton_sku->total_qty,2)` instead of a strict float `!==`; the carton inventory query uses `Helper::resolveCustomerIdFromAggregator($order->customerId)` like every other balance query. **Downstream effect to be aware of:** `StandardOrderPickingService.php:491-497` and `OutboundSkuValidationHelper::validateSkuBasedOnIsAllocatedFullCarton` read this flag (when all tasks of a pick are full-carton, SKU barcode entry is not required and the full-carton branch runs; the column was added 2026-04-21). Fixing B switches that dormant picking behavior on for every pick whose cartons are fully allocated. Hence its own toggle, **shipped OFF** (`ALLOCATION_FIX_FULL_CARTON_FLAG=false`): the code is in place, `is_allocated_full_carton` stays `false` as today, and it is switched on per environment only after the picking team has confirmed the full-carton pick behavior (take all pending qty of the flagged tasks, and, for customers with `is_validate_full_carton_while_picking`, no SKU barcode scan). Checklist for turning it on: pick a fully allocated carton on staging end to end, verify the quantities taken, verify a mixed pick (some tasks flagged, some not) still asks for the SKU, then enable.
- **C. `previous_assignee_null_check`.** `assignNewPickingTasksToPreviouslyAssignedUser` (:1383) dereferences `$assignmentable_task->r_users` before its null check; today that throws inside the `try`, is swallowed, and skips `updateOrderAndOrderSkusLastStatus()` (order status left stale). Fix: null-safe lookup.
- **D. `deterministic_tie_break`.** Add `inventory_balances.id ASC` as the last ORDER BY term (after the preferred-carton `CASE`). Legacy orders by `inbounded_at` / `exp_date` / etc. with no tie-breaker, so MySQL returns tied rows in unspecified order and any plan change can reorder them; a final `id` makes both engines deterministic and exactly comparable.
- Note: `storeAssignmentablePickings` / `getPreviousAssignedUserForOrder` use the order's own `customerId` consistently for create and lookup; that is self-consistent and is left as is.

### What the journaled allocator must reproduce exactly
From the same quiescent starting state, for every scenario: picking-task rows (order_sku, sku, inventory_balance, location, qty, rule, pick sequence, package, assignment, `is_allocated_full_carton`), final `inventory_balances` (`available_qty`, `allocated_qty`), final master `inventories` (`reserved/demanded/available/damaged`), order-sku and order statuses, `AssignmentablePicking` rows, partial-allocation outcomes (options 0/1/2/3, all-or-nothing restore). **Both engines read the same four `legacy_fixes` toggles**, so they stay identical for any toggle combination (journaled implements both the fixed and the unfixed branch of each). The equivalence harness runs the matrix: all defaults (A, C, D on, B off), plus B on, plus each of A, C, D off.

### Things that are not bit-for-bit knowable (named, not hidden)
1. **Float equality** in the full-box path (`HAVING SUM(available_qty) = pending_qty` on `double` columns): reproduced with the same rounding; dedicated fractional-qty fixtures (e.g. 0.1+0.2). Pre-aggregating quantities per SKU may differ from legacy's sequential arithmetic at 1e-15 (these `double` columns already hold such dust, see `fix:inventory`'s `qtyDustSql`); equivalence is asserted at 2 decimals.
2. **String/collation semantics** (`utf8_unicode_ci`: case/accent-insensitive equality on lot/batch/serial/barcode/zone names). Never re-implemented in PHP; MySQL keeps doing all filtering.
3. **Concurrent writers during a run.** Legacy reads live data per line, so its output under concurrency is already timing-dependent. The contract holds for a quiescent start; under concurrency the journaled allocator never over-reserves but need not equal what legacy would have done at that instant.

### The only intentional differences between the engines
(a) a crash/kill/exception never leaves reserved-without-task stock in the journaled engine; (b) a lost race on a balance is detected and re-planned instead of clamped to 0 (journaled only); (c) the journaled engine rethrows instead of swallowing exceptions. Legacy keeps its swallow/clamp behavior (changing it would abort whole cron loops); it is mitigated by the pool lock and recovery in Step 4.

## Step 2b — Large-order path

In pools that run the **journaled** engine, orders with more than `config('allocation.large_orders.allocatable_line_threshold')` allocatable lines (default **2000**) are never allocated by the instant listener or `process:standard-order`; they belong to the large-order cron. (Pools still on the legacy engine are not routed this way; see item 9 below.) The number lives only in config; the endpoint, both crons, the listener backstop and the tests all go through `AllocationEngineResolver::isLargeOrderLineCount(int $n): bool`.

**Decisions:**
- **Disabled warehouses:** the large-order cron processes a large order only if the warehouse has `enable_auto_allocation_for_standard_order` on (`CacheHelper::getAutomaticAllocatableWarehouseIdsForStandardOrder()`), **or** someone explicitly requested allocation.
- **Manual click = mark only:** `instant_order_allocation` keeps its validations (locked, status, `is_allocating`, creation completed, picking-strategy rules), then stamps `orders.allocation_requested_at = now()`, dispatches nothing, and answers "queued for large-order allocation". Latency: up to one cron interval (default 30 min).
- **Threshold counts allocatable lines, computed live** (no stored count): lines in the statuses the allocator loads (`WMS_CONFIRMED`, `WMS_OUT_OF_STOCK`, `WMS_PARTIALLY_ALLOCATED`), via one grouped query per candidate chunk (`SELECT orderId, COUNT(*) … WHERE orderId IN (chunk) AND last_status_id IN (…) GROUP BY orderId`), backed by an index on `order_skus (orderId, last_status_id)` (verify/add). A large order that becomes mostly allocated drops under the threshold and returns to the normal path; ownership is decided at pick time.
- **Pool lock per chunk** (journaled engine): a large run holds the pool lock only while planning/applying each chunk, so small orders and other large orders of the same customer interleave. All-or-nothing orders are compensated through the journal if a later chunk cannot be satisfied. Large runs always use the `batched` selection and the journaled run/lease/fencing.

**Batching: each run takes up to `large_orders.orders_per_run` (default 10) large orders and allocates them one after another in the same process** (your decision: a batch of 10, sequential; no child processes, no parallelism):
1. `allocation:process-large-orders` (schedule from `large_orders.cron_expression`, default every 30 min; `withoutOverlapping(expiresAfter)` with `expiresAfter` from `large_orders.overlap_expires_after_minutes`; `runInBackground`) first runs `AllocationRunRecovery::compensateExpired()`. **Overlap mutex lifetime (verified in `vendor/.../Scheduling/Event.php:667` and `CacheEventMutex.php:42`):** `withoutOverlapping($expiresAt = 1440)` takes a cache lock with TTL `expiresAt*60`, released only by `schedule:finish` after the background process ends; if the process is killed (deploy, OOM) the mutex stays until the TTL, and lease recovery does not touch it. So the TTL must be just above the *bounded* worst-case run, not a generous number. The worst case is bounded by design: no new order starts after `cron_start_budget_s` (default 1500 s) and a single order is aborted after `large_orders.max_order_runtime_s` (default 3600 s: the journaled run is compensated and the order deferred, see Step 3 failure outcomes), so a run lasts at most 1500 + 3600 s = 85 min. `overlap_expires_after_minutes` defaults to **100** (85 + margin), and a test asserts `overlap_expires_after_minutes * 60 >= cron_start_budget_s + max_order_runtime_s`. If the mutex ever expires under a still-running master, a second master is harmless for correctness: the unique `allocation_runs` row per order and the pool lock stop double allocation (note `Order::updateIsAllocatingFlag` is NOT atomic, it does `refresh()` then `update()`, so the journaled start must rely on the unique run row, not on that flag). Deploy runbook: run `schedule:clear-cache` after deploys/restarts, and alert if the last successful large-order run is older than two intervals.
2. It selects eligible orders oldest first (same filters as `ProcessStandardOrderCommand`: status confirmed/OOS/partial, standard B2B/B2C types, `is_locked = false`, `is_creation_completed`, `is_allocating = false`, `insertTime <= now-5min`, retry schedule through the same `AllocationAttemptHelper` counters), keeps those whose live line count is above the threshold AND (warehouse auto-on OR `allocation_requested_at` set).
3. It takes the first `orders_per_run` eligible orders (oldest first) and allocates them sequentially, calling the factory/engine for each. One process, one DB connection set, no shared state: simplest and lowest resource use. If a pool is busy for one order, that pool's remaining orders in the batch are skipped for this run (see "Cron behavior" in Step 3) and the batch is topped up from the next eligible orders of other pools, so a busy pool does not shrink the batch.
4. **Start gate, not a kill:** `cron_start_budget_s` (default 1500) stops *starting* new orders once exceeded, even if fewer than `orders_per_run` were done; an order already running is never killed at the budget (killing would waste a nearly finished run, since a journaled run restarts rather than resumes). Because `withoutOverlapping` skips the next tick while this run is still going, a slow batch simply delays the next one; the process has no kill timeout, and the journaled lease/compensation covers a deploy-time kill.
5. Throughput note: sequential means total time is the sum of the 10 orders (for a few-thousand-line order, minutes each with the batched selection), so a batch can outlast the 30-minute interval; `orders_per_run`, `cron_expression` and `cron_start_budget_s` are the knobs. Parallel children were considered and declined.
6. Each order acquires the pool lock with `cron_wait_seconds`; on a busy pool it is **deferred** (no attempt counter change) as described above.
7. **`allocation_requested_at` is cleared only when a run completes**, inside the journaled finalize transaction (same commit as `run -> completed`). It is **kept** when a run is compensated (crash, kill, lost-race exhaustion, lock-wait failure) or deferred (busy pool), so an order in an auto-off warehouse is never stranded by an infrastructure failure and the next cron tick retries it without a new click. A request is honored regardless of the retry-schedule wait (an explicit user request ignores the 2h/6h/24h backoff; auto-on orders without a marker still follow it). A requested order that completes but is still out of stock/partial follows the normal retry schedule only if the warehouse is auto-enabled; otherwise it waits for another click. To keep a poison order from looping forever, compensations count against the order's attempt counter only after `recovery.free_compensations_per_order` (default 2) compensated runs in 24h; the first ones are treated as infrastructure kills and do not move `allocation_counter`.
8. Resource note: one PHP process, memory bounded by chunked reads (~200 SKUs at a time) and released per order.
9. **Large-order routing applies to journaled pools only.** `AllocationEngineResolver` decides legacy vs journaled by the rollout flags *first*; only a pool that resolves to journaled is subject to the threshold routing above (endpoint marks instead of dispatching, `process:standard-order` and the listener skip it, the large cron owns it). A pool that still resolves to legacy keeps today's behavior for every order size: the instant endpoint dispatches as before and `process:standard-order` allocates large orders as it does now. Reason: the legacy engine holds the pool lock for the whole run and cannot renew it, so a multi-minute legacy run could outlive its TTL and silently lose mutual exclusion (see `legacy_run_ttl_*` in Step 3); and sending legacy-pool large orders to the large cron would only move that risk, while skipping them in both places would strand them. Consequence to accept: until the journaled engine is enabled for a pool, its large orders are still exposed to the old kill/orphan failure (mitigated by Step 4 hardening); enabling the journaled engine for the pools that receive large orders is the first rollout step.
10. Visibility: dedicated log lines per run (started, deferred, finished, duration, lines); the UI shows "queued for large-order allocation" when `allocation_requested_at` is set and the order is not `is_allocating`.

## Step 3 — Journaled algorithm

### Persistence model (crash-safe, concurrency-safe)
1. **Pool mutex = new `AllocationPoolLock`, NOT `ConcurrencyControl::execute`.** A stock pool is `(organization_id, warehouseId, aggregator-resolved customer)`; every allocator of that pool competes for the same `inventory_balances` rows. The lock `alloc:{org}:{wh}:{poolCustomer}` allows one allocator at a time to plan/apply on a pool (prevents silent over-reservation from the clamp at :1125 and makes orphan recovery safe because no other allocator has in-flight task-less reservations). It does not block pickers/putaway/adjustments (they never take it; they are covered by the conditional `UPDATE … WHERE available_qty >= q` and row locks).
   - **Why not `ConcurrencyControlService::withLock`** (`app/Services/WMS/Concurrency/ConcurrencyControlService.php:37`): its `Cache::lock($key, 10|30)` number is a **TTL**, so a run longer than 10-30s silently loses mutual exclusion; it wraps the operation in `DB::transaction()` (the long transaction this design rejects); it retries 3 times with ~0.1-0.3s sleeps then throws. `executeTransactionWithDeadlockRetry` in the same class is still used for the short chunk transactions.
   - **API** (built on `Cache::lock`, Redis; same pattern as `FixInventoryFromInventoryBalance` and `UpdateMessageEventListener`): `block($seconds)` waits up to N seconds and returns a handle or `null`; `tryAcquire()` = `block(0)`; owner token; release in `finally`; no wrapping transaction. No caller ever proceeds without the lock. **Laravel 9 gap (verified in `vendor/laravel/framework/src/Illuminate/Cache/Lock.php`):** `isOwnedByCurrentProcess()` is `protected` and the lock has no `extend()`/renew method, so `AllocationPoolLock` wraps/subclasses `RedisLock` to add `isOwned()` (owner-compare) and `extend($seconds)` (owner-checked `PEXPIRE` via a small Lua script, atomic).
   - **Hold time and TTL:** journaled takes it per chunk (plan + apply, seconds) with `journaled_chunk_ttl_seconds` (default 60), **extended during planning** (`extend()` between selection queries) so a slow chunk cannot outlive its TTL, and a dead holder still blocks the pool for at most one TTL. Legacy must hold it for the whole run and cannot renew it, so its TTL depends on the caller: `legacy_run_ttl_instant_seconds` (default 240: the queue kills at 180 s, so the lock cannot be needed longer) and `legacy_run_ttl_cron_seconds` (default 3600, for `process:standard-order` which has no kill timeout). After a legacy run the adapter checks `isOwned()`; if the lock expired mid-run it logs an error with the pool key and run duration (mutual exclusion was lost, so recovery must treat that run's stock as suspect). A dead legacy holder blocks its pool until the TTL expires.
   - **Lock participants (fix for the unlocked-reserver hazard):** the pool lock is only a valid basis for orphan recovery if every *batch/queue* path that reserves stock from the pool takes it. Verified reservers besides the standard allocator: `FulfillmentTaskHelper::updateInventoryBalanceTable` (called from `CreateFulfillmentTaskCommand`, `InstantAllocationEventListener`, `SkipTaskHelper`, `ProcessB2BTransferOrderBatch`: it moves `available_qty` to `allocated_qty` *before* the fulfillment task row exists) and `AllocateRCOOrderHelper::updateInventoryBalance` (from `ProcessRCOOrderCommand`, `OrderController` :3187/:4020, `CancelRcoOrderCaseEventListener`: raw `UPDATE` of whole totes). These call sites take `AllocationPoolLock` (cron/queue callers with the `cron_wait_seconds`/`instant_wait_seconds` rules below; the two OrderController HTTP calls with `skip_wait_seconds`) before legacy orphan recovery is allowed to auto-restore anything. Interactive picker actions (e.g. switch-task in `StandardOrderPickingService` :1806, which creates the task in the same request) do not take the lock; they are covered by the safety margin below.
   - **Recovery safety margin:** auto-restore (journaled compensation excepted, it works from its own journal) only touches balances whose `updated_at` is older than `recovery.orphan_min_age_seconds` (default 300), so a reservation made moments ago by an unlocked writer is never mistaken for an orphan. Until all participants above take the lock, legacy recovery runs in **report-only** mode (`recovery.legacy_auto_restore = false`: log the orphans found, restore nothing).
   - **What it does and does not serialize:** different *processes* on the same pool. A single cron run takes/releases it per order (journaled: per chunk) and never blocks on itself: a customer with 100 eligible orders still gets all 100 allocated in one tick. Different pools use different keys and never wait on each other.
   - **Cron behavior** (`process:standard-order`, `allocation:process-large-orders`): wait up to `cron_wait_seconds` (default 30). If still busy, **defer the whole pool** for this tick: skip this order and the rest of that pool's orders, continue with other pools. A deferred order does not call `AllocationAttemptHelper::updateAfterAllocationAttempt` (that call counts any non-ALLOCATED outcome as a failed attempt: `allocation_counter + 1`, `last_allocation_tried_at = now`, retry pushed to 2h/6h/24h, and at `LOCK_THRESHOLD = 18` sets `is_locked = true`, so counting a busy pool would delay and eventually lock orders that were never tried). Deferred orders keep their old `last_allocation_tried_at`, so they stay first in line next tick. Per-run log: allocated, deferred per pool, total lock wait.
   - **Instant paths** (instant listener, newly-added-SKU listener): **short wait, many re-dispatches, never hold the single worker.** The `iqh-instant-allocation` queue has `maxProcesses = 1` (`config/horizon.php:270`) and is shared by `InstantAllocationStandardOrderEventListener`, `InstantAllocationEventListener` (RCO/B2B-type orders) and `AutoCloseAsnEventListener` (verified), so a worker blocked on one busy pool delays every other customer's allocations and ASN auto-close behind it. Therefore wait only `instant_wait_seconds` (default **8**). Still busy: the listener re-dispatches itself after `instant_redispatch_delay_seconds` (default **20**) with an attempt counter, up to `instant_max_redispatches` (default **30**, about 10 minutes of waiting in total, mostly off the worker), keeping `is_allocating = 1` while waiting and not calling `updateAfterAllocationAttempt`. Budget exhausted: reset `is_allocating = 0`, log an error with the pool key, fail the job visibly (no attempt-counter change, no unlocked run). Skip-switch (`allocateSkippedTaskQty`, inside an HTTP request): waits `skip_wait_seconds` (10), then returns `false` (its existing "could not switch").
2. **Run + lease.** `allocation_runs(id, order_id, token, status running|completed|compensated, lease_until, started_at, finished_at, line_count)`, one running run per order (unique key). Each chunk renews `lease_until` by `journaled.lease_seconds` (default 600). `is_allocating` stays for UI/command compatibility, driven by the run lifecycle.
3. **Reserve, per CHUNK (not per line), one short tx, set-based** (the journal adds no per-reservation statement):
   - `SELECT id, available_qty FROM inventory_balances WHERE id IN (chunk) ORDER BY id FOR UPDATE` (fixed lock order).
   - **Lock ownership check right before the transaction:** the chunk holds the pool lock (TTL 60 s, extended during planning). Immediately before opening the apply tx, call `isOwned()`; if the lock was lost (expired, Redis failover), do **not** apply: re-acquire (`chunk_lock_wait_seconds`) and **re-plan the chunk** from fresh data. The check cannot be atomic with the tx, so it is a guard against wasted/stale plans, not the correctness mechanism; correctness still comes from the conditional `UPDATE` below, the row locks and the run fencing, and must hold even with the lock disabled (tested).
   - One conditional multi-row `UPDATE … SET available_qty = available_qty - CASE id … END, allocated_qty = allocated_qty + CASE id … END, updated_at = now() WHERE id IN (chunk) AND available_qty >= CASE id … END`; `affected_rows` must equal the chunk size, else roll back the chunk and re-plan the remaining lines (bounded by `lost_race_max_retries`, see failure outcomes below).
   - One multi-row `INSERT … ON DUPLICATE KEY UPDATE qty = qty + VALUES(qty)` into `allocation_run_reservations(run_id, balance_id, qty)` (unique `(run_id, balance_id)`), plus the lease renewal, in the same tx. Journal cost = 2 statements per chunk.
3b. **Mid-run failure outcomes (defined, not left open).** A journaled run can fail in four non-crash ways; all four end the same way:
   - **(i) A chunk cannot get the pool lock** within `chunk_lock_wait_seconds` (default 60 for cron/large runs, `instant_chunk_lock_wait_seconds` default 10 for instant runs), including after a lost-lock re-acquire.
   - **(ii) `lost_race_max_retries` is exhausted** (default 3): the chunk's conditional `UPDATE` keeps failing because other writers keep taking the stock.
   - **(iii) The single-order runtime cap is hit** (`large_orders.max_order_runtime_s`, default 3600).
   - **(iv) The lease was lost** (the run was compensated by recovery): finalize/fencing aborts and writes nothing.
   Outcome for (i)-(iii): **compensate the run through the journal (restore every reserved qty), mark it `compensated` with a `reason` (`lock_wait` | `lost_race` | `runtime_cap`), clear `is_allocating`, keep `allocation_requested_at`, and defer the order with NO change to `allocation_counter` / `last_allocation_tried_at`** (a deferral is not a failed allocation attempt; same reasoning as the busy-pool rule). The order is eligible again on the next tick. Deferrals are counted per order in `allocation_runs`; after `recovery.max_consecutive_deferrals` (default 10) the order is flagged in the log/alert channel (it is never auto-locked for deferrals). Outcome for (iv): nothing to do, recovery already restored the stock. A run that ends this way is logged with order, pool key, chunk number, lines done and reason.
4. **Finalize (one short atomic tx, set-based).** Lock run row, verify `status = running AND token = mine` (fencing: a zombie worker that was already compensated writes nothing). In the same tx: picking tasks (multi-row `INSERT`, `task_insert_rows` per statement, capped by `@@max_allowed_packet`), master `inventories` (one `SELECT … ORDER BY sku_id FOR UPDATE` + one multi-row `UPDATE … CASE` per SKU chunk, quantities pre-aggregated per SKU: legacy's sequential negative-demand branch composes to `demanded = max(D − Σq, 0)`, `available −= max(Σq − D, 0)`, `reserved += Σq`, `damaged −= Σq` for non-good stock), order-sku statuses (≤3 `UPDATE … WHERE orderskuId IN (…)`), assignment rows, order status via the existing `evaluateAndUpdateOrderLastStatus()` (once), run → `completed`, `is_allocating = 0`. Single commit point.
5. **Compensation.** `AllocationRunRecovery::compensate($run)`: tx, lock run, if still `running` apply the inverse delta of each journal row (`available += q`, `allocated -= q`, same floor-at-0 as `restoreAllocatedQtyInInventory`), mark `compensated`. Idempotent, delta-based (commutes with other writers). Restart, never resume. **Triggers:** listener catch and `failed()` (fires on `MaxAttemptsExceededException`); start of any new run for the order; start of every `process:standard-order` tick (~10 min) and every large-order cron run (~30 min); and the **hourly** `allocation:recover-stale-runs` as the final backstop (`recovery.sweeper_cron_expression`, default `0 * * * *`). Only runs whose lease has expired are touched. Worst case a dead run's stock stays blocked until the first of these fires after the lease expires (typically ≤ 10-30 min, never more than an hour plus the lease).
6. **Deadlocks.** Ordered locks (run row → balances by id → inventories by sku_id), short transactions, `executeTransactionWithDeadlockRetry` (`deadlock_max_attempts`, `deadlock_base_wait_ms`). Guarantee: a deadlock never fails or corrupts an allocation (it retries); not "InnoDB never reports one".
7. Nested transactions: the skip flow may already hold a transaction (savepoints); finalize must tolerate an outer tx (tested).

### Selection strategy (where the speed comes from), two layers behind `journaled.selection`
**`batched` is the target design**; `per_line` is the reference/fallback and first soak step. Both pass the same differential harness.
- **`per_line`:** per-line selection as legacy with behavior-neutral speedups: `JOIN warehouse_locations` instead of `whereHas`/ORDER BY scalar subquery, composite index on `inventory_balances (organization_id, warehouse_id, customer_id, sku_id, available_qty, is_on_hold)`, per-run memoization (location-type lists, aggregator customer id, rules), no re-SELECT before locking. Reservation applied per line, so later lines see earlier ones.
- **`batched`:** plan first, apply after.
  - Group lines by selection signature (order-sku attribute conditions + exact/non-exact pass + rule filters); one SQL per group over a chunk of `chunk_sku_count` SKUs (`sku_id IN (…)`; exact pass matches `(sku_id, sku_barcode)` pairs). MySQL still does all filtering, collation and ORDER BY (ties by `id`).
  - Simulate reservations in memory: a per-run `reserved[balance_id]` map reduces `available_qty` for later lines, rows reaching 0 drop out; the pass-1/pass-2/rule-loop logic (with fix A) runs over the in-memory pool. After fix A the default branch's second pass is provably a no-op when pass 1 left a remainder (pass 1 drained every candidate), so the journaled engine skips that duplicate query; the harness proves it.
  - Full-box / full-carton / full-package: SQL fetches qualifying rows; the group `SUM(available_qty)` vs `pending_qty` (`>=` or `=`) is recomputed in PHP on net-of-reservations quantities. Best-fit and the preferred-carton tie-break (`CASE WHEN carton_number IN (…)`, after the allocation-type keys, then `id`) run on the in-memory rows.
  - Nothing is written during planning, so all-or-nothing orders need no restore. Apply in chunks, conditional on `available_qty >= q`; a mismatch re-plans only the remaining lines from fresh data.

## Step 3b — Query-efficiency budget (journal included)

Principle: statements scale with **chunks**, not lines; the journal piggybacks on statements that already exist.

| Phase | Legacy (per line) | Journaled `batched` |
|---|---|---|
| Candidate selection | 2-4 `SELECT`s per line with `whereHas` + ORDER BY scalar subquery | one `SELECT … JOIN warehouse_locations` per (signature × SKU chunk × pass); `pick_sequence` returned in the same row (no `r_location` eager-load per line) |
| Reservation | 1 tx + lock `SELECT` + `save()` per balance | per chunk: 1 lock `SELECT`, 1 conditional multi-row `UPDATE` |
| Journal | none | per chunk: 1 `INSERT … ON DUPLICATE KEY UPDATE` + lease update, same tx |
| Hydrating chosen balances | 1 `SELECT` (whole rows) | 1 `SELECT … WHERE id IN (chosen)` per chunk |
| Picking tasks | 200-row inserts | `task_insert_rows` per insert |
| Master `inventories` | `SELECT` + 1-2 `save()` per task | 1 lock `SELECT` + 1 multi-row `UPDATE` per SKU chunk |
| Order-sku statuses | 1 `save()` per changed line | ≤3 `UPDATE`s |
| Order status / assignment | once | once (existing methods) |

Target for a ~4700-line order: a few hundred statements (selection ≈ 50-300, apply ≈ 50, finalize ≈ 40) versus ~15-25k. Targets, asserted by a query-count budget test and confirmed by profiling, not promises.

Techniques (all behavior-neutral):
- Keep the Eloquent builder for selection (so `OrganizationScope` / `RelatedCustomerScope` still apply, including the HTTP skip-switch path with an authenticated user) but use `->toBase()->get()` to skip model hydration; bulk writes use the query builder (scopes bypassed exactly as legacy's `withoutGlobalScopes()` calls).
- Set `updated_at` explicitly in bulk updates. Checked: `InventoryBalance` (only `creating`, not hit), `Inventory`, `OrderSku`, `StandardOrderPickingTask` have no saving/updated hooks or observers, so bulk writes lose no side effects. Re-verify at implementation and fail the build if one appears.
- Narrow selects during planning; full rows only for chosen balances.
- Indexes: `inventory_balances (organization_id, warehouse_id, customer_id, sku_id, available_qty, is_on_hold)`; confirm `warehouse_locations` join keys, `wms_standard_order_picking_tasks (order_id, order_sku_id)`, `order_skus (orderId, last_status_id)`; `allocation_run_reservations` unique `(run_id, balance_id)`; `allocation_runs (status, lease_until)`.
- Bounded memory (chunks, rows released per chunk); one lease renewal per chunk; aggregated logging; `CASE id WHEN …` multi-row updates (portable MySQL).

## Step 4 — Hardening the legacy path

The legacy allocator has no journal, so it **cannot** be made crash-proof like the journaled one. Around it:
- Listener `$timeout` aligned with the supervisor. In journaled pools large orders never run on the queue; legacy pools keep today's routing (Step 2b item 9), so a large legacy-pool order can still be killed at 180 s on the instant queue until that pool is moved to the journaled engine.
- Legacy runs take the pool lock (`AllocationPoolLock`, whole-run hold, `legacy_run_ttl_instant_seconds` / `legacy_run_ttl_cron_seconds`, ownership checked after the run) via the adapter. Recovery is safe only while **every** batch/queue reserver also takes the lock (the participants listed in Step 3 item 1: fulfillment-task and RCO paths too); until those call sites are updated, legacy recovery is **report-only** (`recovery.legacy_auto_restore = false`) and, once enabled, only restores balances older than `recovery.orphan_min_age_seconds`.
- Listener `failed()` and catch for a legacy run: **never just reset `is_allocating`.** Under the pool lock, restore this order's orphaned reservations (new `LegacyRunRecovery` built on `OrphanedAllocationQtyHelper`, restricted to the pool and the order's SKUs/balances), and only then reset the flag. If recovery cannot run, leave the flag set and log loudly (fail closed); resetting over live orphans would let the order re-reserve the same stock twice.
- Because the legacy helper swallows its own exceptions (:135/:200), the listener also runs the same scoped orphan check after every legacy run that ends with the order still unallocated.
- This is best-effort recovery, not the guarantee; the guarantee exists only in the journaled engine, which is why the rollout moves customers onto it.

## Step 5 — Rollout flag and phases

`AllocationEngineResolver`: master off → legacy; customer in `except_customers` → legacy; otherwise journaled if the pool matches ANY of the org / warehouse / customer lists (union: each phase adds an id). Emergency kill without redeploy: cache key `journaled.kill_cache_key` (default `allocation:journaled:kill`) forces legacy.
- Evaluate on the **stock-pool key** `(organization_id, warehouseId, Helper::resolveCustomerIdFromAggregator(customerId))`, not the order's raw customer, so aggregator children sharing a pool never split across engines.
- Engine chosen once per run. A journaled run in flight when the flag is flipped off finishes or is compensated (recovery never consults the flag). A legacy start on an order with a stale journaled run compensates it first.
- After an env change run `config:cache` + `horizon:terminate` (workers cache config). `MainConfigurationHelper` only scopes warehouse+customer (no organization), so it is not used for this flag.

| Phase | Scope | Gate to advance |
|---|---|---|
| 0 | Deploy with `journaled.enabled=false`. Legacy fixes A, C, D are live at this point (not phased; toggle off in config if needed); fix B ships OFF. | migration ran, smoke test, watch allocation quantities for the fix-A effect |
| 0b | Enable fix B (`ALLOCATION_FIX_FULL_CARTON_FLAG=true`) on staging, then prod, after the picking team signs off | full-carton pick verified end to end (see Step 1 fix B checklist) |
| 1 | Staging, all journaled, `per_line` | differential/crash/concurrency tests green |
| 2 | Staging, `batched` | same harness + scale test (5000 lines) |
| 3 | Prod: first chosen customer (one that receives large orders), `per_line` | days with 0 orphans for that pool, 0 stale runs, compensations all explained |
| 4 | same customer → `batched` | same |
| 5 | + next customer, then warehouse 1, then organization 1, then everyone | same per step; then schedule legacy removal |

Each journaled run logs to a dedicated channel: duration, lines, selection mode, reserve retries, lost races, compensations, mutex wait. Rollback at any phase: flip env or set the cache kill key; no data migration.

## Step 7 — Process and verification

Process (project rules `test-before`, `senior-engineer-stance`, `concurrency`): **tests first.** Before any production change, characterization tests of the current legacy allocator for every scenario below; for fixes A-D the tests assert the *corrected* behavior and must fail on today's code, then pass after the fix. These tests are also the journaled allocator's acceptance suite.
1. **Differential harness** (both allocators side by side): seeded random fixtures (≥1000) covering every allocation type (standard/FIFO/LIFO/FEFO/LEFO/FMFO/GRN/order-UOM/full-box/full-box-then-standard/full-carton/full-package/best-fit), location priorities, exact vs non-exact barcode, partial handling 0/1/2/3, every order-sku attribute filter, zone/zone-group/location rule filters, return-location priority, carton plan, repeated SKU across lines, fractional qty, insufficient stock, on-hold/inactive/locked locations, staging/cancelled/missing exclusion, already-partially-allocated order, and explicit cases for fixes A-D. Run both on cloned data (`DatabaseTransactions`, `_test` DBs) and assert the Step 1 identity contract (exact, thanks to fix D). Run for `per_line` and `batched`.
2a. **Pool-lock tests:** a cron run with 100 orders of one pool allocates all 100 in one tick; a lock held by another process makes the cron wait `cron_wait_seconds`, then defer the whole pool while still processing other pools; deferred orders keep `allocation_counter` / `last_allocation_tried_at` unchanged and stay first next tick; the instant listener re-dispatches with an attempt counter, keeps `is_allocating = 1` while waiting, and after `instant_max_redispatches` resets the flag and fails visibly with no attempt-counter change; skip-switch returns `false` after `skip_wait_seconds`; lock released in `finally` on exceptions; a dead holder frees after its TTL; no path allocates without the lock.
2. **Resolver and routing tests:** every flag combination, aggregator child → pool key, cache kill; allocatable line counts at threshold-1 / threshold / threshold+1 with the default and an overridden config value; auto-enabled vs auto-disabled warehouse with and without `allocation_requested_at`; the endpoint stamps instead of dispatching; `ProcessStandardOrderCommand` and the listener skip/refuse large orders; the large-order master ignores small and disabled-and-unrequested orders; request is one-shot; an order dropping below the threshold returns to the normal path; per-chunk lock lets a small order interleave; an all-or-nothing large order is compensated when a later chunk fails.
2c. **Failure-path and lock-safety tests:** (a) `allocation_requested_at` survives a compensated run, a deferral and a busy pool, and is cleared only by the finalize commit; a requested order in an auto-off warehouse is retried on the next tick after an injected crash; (b) the first `free_compensations_per_order` compensations leave `allocation_counter` untouched, later ones increment it; (c) lock lost between planning and apply (expire the Redis key in the test): the chunk is not applied and is re-planned; with the lock disabled entirely, two concurrent journaled runs never over-reserve (conditional `UPDATE` + fencing); (d) a chunk that cannot get the lock within `chunk_lock_wait_seconds`, `lost_race_max_retries` exhausted, and `max_order_runtime_s` exceeded each compensate the run, clear `is_allocating`, keep the marker and leave `allocation_counter` / `last_allocation_tried_at` unchanged, with the right `reason`; (e) the instant listener waits at most `instant_wait_seconds`, never blocks the worker longer, re-dispatches up to `instant_max_redispatches`; other jobs on `iqh-instant-allocation` (ASN auto-close, RCO instant allocation) are not delayed by a busy pool; (f) `AllocationPoolLock::extend()` / `isOwned()` are owner-checked (a non-owner can neither extend nor release); (g) fulfillment-task and RCO call sites take the lock; legacy recovery in report-only mode restores nothing, and with auto-restore on skips balances newer than `orphan_min_age_seconds`; (h) routing: a legacy-resolving pool's large order keeps today's path (endpoint dispatches, `process:standard-order` allocates it), a journaled pool's large order is marked and owned by the large cron, no order is skipped by both; (i) `overlap_expires_after_minutes * 60 >= cron_start_budget_s + max_order_runtime_s`; a killed large-order run leaves the mutex until its (bounded) TTL and the next run after that proceeds; (j) a second large-order master started after mutex expiry cannot double-allocate an order (unique run row), and the journaled start does not rely on `updateIsAllocatingFlag`.
2b. **Large-order batch tests:** a run takes at most `orders_per_run` orders, oldest first, strictly one after another; a busy pool's remaining orders are skipped and the batch is topped up from other pools; no new order starts after `cron_start_budget_s` but a running one is not killed; two overlapping runs are prevented by `withoutOverlapping`; `orders_per_run` overridden in config is honored.
3. **Crash tests:** exception after N lines; `kill -9` mid-run on staging; balances equal the pre-run snapshot after compensation, `is_allocating = 0`, rerun equals a fresh run; zombie finalize is fenced out. Legacy path: kill → `failed()` recovery restores orphans, flag reset only after recovery. Sweeper hourly schedule and every other recovery trigger exercised.
4. **Concurrency tests:** parallel allocators on competing orders (both engines mixed on one pool), allocator vs concurrent picking/putaway; no balance negative or over-reserved; orphan scan = 0; deadlock retry exercised.
5. **Efficiency tests:** (a) query-count budget on a seeded 5000-line order, asserting a ceiling and that statement counts grow with chunks, not lines (compare 500 vs 5000 lines); (b) staging scale run recording wall time, statement count and peak memory for legacy vs journaled `per_line` vs `batched`, with a batch of 10 large orders run sequentially; (c) journal overhead (journaled `batched` with the journal insert disabled in a test build; expected negligible).
6. Full suite vs documented baseline (32 pre-existing failures, memory: test-suite-baseline); `SingleOrderPickingSkipTaskTest` overload mock still passes.
